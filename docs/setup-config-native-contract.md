# Native Setup configuration contract

This is the native-derived translation contract. The configuration candidate
implements factory defaults, presets, session Custom storage, separate Main
working/committed values, cursor policies and native input repeat through real
menu callers. See `docs/setup-config-implementation.md` for its exact replay
scope and independent-audit status. Disk saving, gameplay/audio consumers and
complete transition timing are not established by these menu proofs.

## Working, committed and saved boundaries

Main edits belong to `$16FB-$1701`, while `$17AB-$17B1` remains committed until
the native handoff. For example, after Arcade→Simulation the working Style is1
and active Rules immediately become Simulation, but committed Style remains0.
`$81:BED5-$BEE4` commits all four Main words before opening either submenu;
`$81:BF59-$BF68` commits them when confirming a match. The shared working buffer
is then reused for that submenu's values. A single C array cannot expose these
two native states accurately at their respective boundaries.

Rules entry `$81:CFCE-$CFDE` copies all13 active Rules into working storage.
`$81:D446-$D50D` adjusts a row; `$81:D47A-$D491` writes the working value and
immediately writes committed Style=Custom(2). This also happens on a clamped
bar press that leaves its value unchanged. The natural Simulation45→45 press
proves this quirk. Active committed Rules stay unchanged while editing.

Rules Start `$81:D516-$D526` copies13 working values to active Rules, then
`$81:D52F-$D537` saves Custom if committed Style is2. `$81:C3D5-$C41D` /
`SaveCustomRules` writes Custom's two byte thresholds and eleven-bit bitmap.
B does nothing; it does not cancel or commit. Reentering Rules restores the
committed edited rows. Returning to Main rebuilds its working values from the
committed Main block and selects row0.

Options uses the same working-buffer distinction, seven values, and does not
mark Style Custom. Normal Start copies seven values through `$82:8EB3-$8EC9`,
then restores the working volume words and applies their gain at `$8ED4-$8EE0`.
Fresh bank82 recomp and Ghidra listings in the reference directories above
independently decode that branch. The original six-journey capture does not
instrument those exact copy-loop boundaries. The separate Main-v3 corpus
records normal Start entry/after-copy/volume-restore/after-gain boundaries at
`$82:8EB3/$8ECB/$8ED4/$8EE4`. Values are unchanged in that particular Options
visit; the separate edited Options journey establishes changed-value commits.
The script also records `$82:8D0A`, a different in-game exit path;
do not mislabel that callback alone as proof that the normal Start branch ran.
The complete action snapshots independently record the normal commit result.

## Every-row input evidence

`rules-v2` executes256 actions, `options-v2`288. Each of the four bar rows has
all46 distinct Left edges and46 Right edges: every0..45 state, every adjacent
step, and both endpoint clamps. Every Boolean row has0→1 and1→0 through both
Left and Right. Music Mode has all three directed edges in each direction.
Every OFF value is reached through the real menu. B-ignore, Start commit and
reentry are recorded. This proves UI/state semantics, not gameplay effects.

Rules cursor movement **clamps** at0 and12. Fresh input observes0→0 on Up and
12→12 on Down; `$81:D3E3-$D3E6` and `$81:D43B-$D43E` agree. The previous C shared
submenu wrap implementation and the regression expecting Rules to wrap were
wrong; the candidate now clamps Rules. Options wraps at0/6 (`$82:8D6A`, `$82:8D85`). Do not replace both menus
with a single wrap policy.

Held-input evidence is separate from individual presses. `$81:AB58-$AC03`
starts a32-frame delay and12-frame repeat interval. When the bar's `$1639`
acceleration flag is set, successive intervals decrement11,10,9,8,7,6,5;
attempting4 clamps the interval to5 and sets `$15E3+controller`. Rules and
Options then add an extra three units before the ordinary one-unit adjustment.
The natural held-input callback offsets are0,32,43,53,62,70,77,83,88, then every5
frames; the last transition switches±1 to±4. `held-v2` captures180-frame holds,
full input timer values, clamp behavior and native before/after routine state.
The candidate replaces the former C pressed-edge-only adjustment with this
producer and its full-word pending consumer `$81:AC04-$AC52`. Rules row redraw
`$81:D59B-$D5AB` sets acceleration for bar rows, even after a clamped Up press.
Options Up/Down explicitly clear acceleration at `$82:8D44/$8D77`. Native
release clears previous/fast/auxiliary state but preserves delay/speed/pending;
a changed nonzero held word preserves fast. These differences are now compared
at native entry/exit and exact input-frame offsets, rather than only after holds.

Main directions also compare whole words, but its remaining buttons use a
different contract: `$81:BE57` tests mask`$C0F0` (B/Y/A/X/L/R), and `$81:BEC7`
opens selected Rules/Options on any word containing those buttons. Therefore
B, Y, X, L, R, A+Start and B+Right can open Rules from Main. Exact Start at
`$81:BF18` confirms a match from any Main row. In Rules/Options, B and combined
words are ignored. Fresh `faces-v1` observes all seven openings and Start from
Main's Rules row; `input-v1` observes mixed words and holds without release.
Hidden button sequences involving `$07FC/$17C3/$17C5` are inventoried but are
not part of this configuration candidate's accepted behavior.

## Disk/SRAM persistence

Custom is retained in SRAM separately from the active configuration. Confirming
the match invokes `$81:C0BA-$C199`, serializing the active values and setting
marker `$70:0004=$DA`. Reload at `$81:C19A` branches to `$C24B` only with that
valid marker; otherwise factory initialization also replaces saved Custom.
Merely committing a submenu in a factory session is not equivalent to the
complete saved-configuration transaction. The exact bytes are:

| SRAM | Meaning |
|---|---|
| `$48` | Mode`<<6` OR Style`<<4` OR Level`<<2` OR Quarter |
| `$49,$4A` | Defensive/Offensive Fouls byte thresholds |
| `$4B-$4C` | Boolean Rules bitmap: rule[i] at bit`12-i`, i=2..12 |
| `$4D,$4E` | Music/SFX volume bytes |
| `$4F` | Music Mode`<<4`, Crowd`<<3`, Slow Dunks`<<2`, Shot Control`<<1`, CPU Assistance |
| `$50,$51,$52` | Team-selection and controller-related state outside this24-value projection |
| `$53,$54,$55-$56` | Separate Custom thresholds and Boolean bitmap |

Two fresh processes loaded files produced by the natural journeys: Custom44/45
and all enabled Boolean Rules survive restart; Options volume0/0 survives
restart. Their loaded arrays, marker, source save hashes and load-branch entry
are retained. Current C session memory retention is not equivalent to this
disk-backed behavior.

Source-only edge caveat: native saved active threshold/volume validation accepts
values below47, although the UI clamps at45. Invalid Mode/Style/Level, malformed
Music Mode or invalid saved team/control values lead to factory reset. Custom
load does not independently clamp its saved byte thresholds. Those corrupt-save
edges have not yet been exercised by controlled native fixtures and must not
be silently normalized to a friendlier policy.

## Bounded translation proposal

1. Separate `working_main[4]` from committed session Main, and add a separately
   retained Custom profile. Put factory defaults and Style/Custom transformations
   in portable typed functions labeled with the addresses and reference names
   above. The main renderer must read working Main; real submenu/match handoffs
   commit it exactly once at their native contract boundary.
2. Route Style input through the preset function. Route every Rules adjustment,
   including no-change clamps, through the Custom-marking path. Rules Start
   commits all13 and updates saved Custom; Options Start commits all7 without
   changing Style. Keep configuration alive across match resets.
3. Give Rules a clamped cursor and Options a wrapping cursor. Translate the
   existing native input-repeat state machine and its bar acceleration; do not
   invent a new timer tuned only to these end states.
4. Implement a portable persisted configuration record that preserves the
   original transaction/validation semantics; distinguish valid saved state,
   saved Custom and current session changes. Do not report disk persistence
   before a fresh-process reload gate passes. Team/control fields require the
   gameplay owner's mapping before claiming complete native SRAM compatibility.
5. Replay the immutable native configuration vectors through production
   functions, then the same action sequences through the real C menu callers.
   Capture internal state where working/committed views differ. Preserve C-only
   regressions separately. Update glyph/default-frame consumers when changing
   factory defaults; original default screenshots contain different values.

The remaining six unconsumed Rules and audio/scheduler/gameplay consumers from
the ownership audit are not solved by presets. Normal matches must still prove
their effects. This corpus excludes graphics/audio equivalence, alternate game
modes, in-game Options paths, every invalid-save input, and the rest of SRAM.

## Production caller diagnostic

`tools/setup_config_runtime_probe.c` accepts only the input schedule and drives
the real C `nba_game_input_update`/`nba_game_tick` callers. It enters Game Setup
directly and waits400 C ticks; this controlled C entry does not test the intro
or claim native frame alignment. `tools/verify_setup_config_runtime.py` compares
all24 committed words at every captured stable boundary and keeps every result.
It does not seed C with expected native values, tolerate differences, or infer
working-buffer/Custom-storage equivalence from committed words. Fresh-process
C disk reload remains explicitly unsupported by this adapter.
